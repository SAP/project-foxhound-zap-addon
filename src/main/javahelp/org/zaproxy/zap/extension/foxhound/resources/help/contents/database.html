Database & Cache

Foxhound uses a two-tier storage architecture to provide both fast access and persistence across ZAP sessions.

Architecture Overview

Two-Tier Storage System

Foxhound stores taint flows in two places:

  • Tier 1: LRU Cache (In-Memory) - Fast access to recently used flows
  • Tier 2: HSQLDB (Persistent) - Complete dataset persists across sessions

Design Goals

  • Performance: LRU cache provides fast access without database queries
  • Persistence: Database ensures no data loss when ZAP restarts
  • Scalability: Handle thousands of flows without degrading performance
  • Reliability: Graceful degradation if database unavailable

LRU Cache (Tier 1)

What is LRU?

Least Recently Used (LRU) is a cache eviction strategy that keeps the most recently accessed items in memory.

  • When cache is full and a new item arrives, the least recently used item is removed
  • Accessing an item moves it to the "most recently used" position
  • This strategy keeps frequently accessed data fast while using bounded memory

Default Configuration

  • Size: 1000 entries (configurable in Options)
  • Range: 1 to 100,000 entries
  • Memory: Approximately 1-2 KB per taint flow entry

Cache Behavior

On Taint Flow Arrival:

  1. New TaintInfo received from Foxhound browser
  2. Added to LRU cache (marks as "most recently used")
  3. Immediately written to database (write-through)
  4. If cache exceeds configured size, least recently used entry is evicted from cache
  5. Evicted entry remains in database, available for lazy loading

On Taint Flow Access:

  1. Request for TaintInfo by ID
  2. Check LRU cache first (fast path)
  3. If found in cache, return immediately and mark as recently used
  4. If not found (cache miss), load from database (lazy loading)
  5. Add loaded entry to cache
  6. Evict least recently used entry if cache full

Tuning Cache Size

Adjust cache size based on your use case:

  • Small cache (100-500):
    • Use when: Memory constrained, testing small applications
    • Trade-off: More database queries, slower access to old flows
  • Medium cache (1000-5000):
    • Use when: Normal testing, moderate flow volume
    • Trade-off: Balanced performance and memory usage (recommended)
  • Large cache (10000-50000):
    • Use when: High-volume testing, analyzing many flows
    • Trade-off: Higher memory usage, better performance
  • Very large cache (50000+):
    • Use when: Intensive analysis sessions, plenty of RAM available
    • Trade-off: May impact ZAP overall performance

Database (Tier 2)

Database Technology

Foxhound uses HSQLDB, the same embedded database used by ZAP core:

  • Lightweight, Java-based SQL database
  • No separate server process required
  • Integrated with ZAP's database lifecycle
  • ACID compliant (Atomicity, Consistency, Isolation, Durability)

Schema Design

Taint flows are stored in a normalized relational schema with 4 tables:

1. TAINT_INFO Table (Parent)

Stores top-level taint flow information:

  • ID (primary key, auto-increment)
  • Timestamp
  • URL
  • Sink name
  • Sink parameters (JSON)
  • Sources (JSON array)
  • Stack trace

2. TAINT_OPERATION Table

Stores individual operations in flow chains:

  • Operation ID (primary key)
  • Operation type (concat, assign, etc.)
  • Location (file path/URL)
  • Line number
  • Script line
  • Function name
  • Result value

3. TAINT_RANGE Table

Stores tainted substrings:

  • Range ID (primary key)
  • TaintInfo ID (foreign key)
  • Begin position
  • End position
  • Tainted string value

4. TAINT_FLOW Table

Links TaintRanges to TaintOperations:

  • Flow ID (primary key)
  • Range ID (foreign key)
  • Operation ID (foreign key)
  • Sequence order

Foreign Key Relationships

  • All foreign keys use CASCADE DELETE
  • Deleting a TaintInfo automatically deletes all child records
  • Maintains referential integrity
  • Prevents orphaned records

Indexes

Optimized for common query patterns:

  • Primary key indexes on all tables (auto-created)
  • Index on TAINT_INFO.timestamp for time-based queries
  • Index on TAINT_INFO.sink_name for filtering
  • Indexes on foreign keys for join performance

Storage Format

Pure SQL Storage:

  • No JSON storage in database (except for small arrays)
  • All TaintInfo fields stored in normalized tables
  • Enables SQL queries, reporting, and analysis
  • Better performance than JSON blob storage

Write-Through Cache Strategy

How It Works

Foxhound uses a write-through caching strategy:

  1. New taint flow arrives
  2. Write to cache (fast, in-memory)
  3. Immediately write to database (persist)
  4. If database write fails, log error but continue (graceful degradation)
  5. Both cache and database stay synchronized

Benefits

  • Data safety: Every flow immediately persisted
  • Consistency: Cache and database always in sync
  • Reliability: No data loss even if ZAP crashes

Trade-offs

  • Writes slightly slower than write-back (but negligible for taint flows)
  • Database I/O on every write
  • Acceptable trade-off for data safety

Lazy Loading

How It Works

Foxhound loads data from database on-demand:

  1. TaintInfo requested (by ID, filter, etc.)
  2. Check cache first
  3. If not in cache (evicted or from previous session):
    • Query database
    • Reconstruct TaintInfo object
    • Add to cache
    • Return to caller
  4. Subsequent accesses hit cache (fast path)

Benefits

  • Bounded memory usage regardless of total flows
  • Fast access to frequently used flows
  • Transparent to callers - they don't know if data came from cache or database

Database Lifecycle

Initialization Phase

  1. ZAP starts, initializes database system
  2. Foxhound's TaintInfoStore.init(Database) called
  3. TaintInfoStore registers TaintInfoTable as database listener
  4. TaintInfoStore registers itself as database listener

Database Open Phase

  1. ZAP opens/creates database
  2. ZAP calls TaintInfoTable.reconnect(Connection)
  3. TaintInfoTable creates tables if they don't exist
  4. TaintInfoTable prepares SQL statements
  5. ZAP calls TaintInfoStore.databaseOpen(DatabaseServer)
  6. TaintInfoStore loads maximum TaintInfo ID
  7. TaintInfoStore optionally loads recent flows into cache (future enhancement)

Runtime Phase

  • Taint flows arrive, written to cache and database
  • Queries served from cache when possible
  • Database queries for cache misses
  • Periodic database maintenance (handled by ZAP/HSQLDB)

Shutdown Phase

  • ZAP closes database cleanly
  • HSQLDB flushes all pending writes
  • Database file closed
  • Next ZAP start loads persisted data

Graceful Degradation

Database Unavailable

If database operations fail:

  • Foxhound continues in memory-only mode
  • LRU cache still works normally
  • Flows not persisted - lost on ZAP restart
  • Alerts still raised, panel still functional
  • Error logged but functionality continues

Recovery

  • Restart ZAP to retry database initialization
  • Check disk space and permissions
  • Delete corrupted database (ZAP recreates it)
  • See Troubleshooting for database errors

Data Management

Clearing Data

Clear All Button:

  • Clears LRU cache immediately
  • Does NOT delete from database
  • Flows reload from database on next ZAP start
  • Use for temporary cleanup of display

Permanent Deletion:

  • Currently: Manually delete ZAP database (advanced users)
  • Future: May add option to permanently delete flows

Session Management

Session Changes:

  • When ZAP session parameter changes (but not null):
    • Cache is cleared
    • Database is NOT cleared (persists across sessions)
  • When session is null (default session):
    • Cache cleared only
    • Database preserves all historical data

Performance Tuning

For High-Volume Testing

  • Increase cache size to 5000-10000 entries
  • Monitor ZAP memory usage
  • Periodically clear old flows if performance degrades
  • Consider filtering to reduce flow volume

For Low-Memory Environments

  • Decrease cache size to 100-500 entries
  • More database queries, but manageable
  • Disable noisy sources/sinks to reduce flow volume

Database Optimization

  • HSQLDB handles optimization automatically
  • Indexes pre-configured for common queries
  • No manual tuning required for most users
